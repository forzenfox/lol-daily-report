# OP.GG 网站接口调研计划书

-   文档版本：V1.0
-   日期：2026-10-21
-   调研对象：OP.GG 韩服《英雄联盟》玩家页面及其前端数据请求
-   样例账号：斗鱼丶胡凯利#2862
-   页面：https://op.gg/lol/summoners/kr/%E6%96%97%E9%B1%BC%E4%B8%B6%E8%83%A1%E5%87%AF%E5%88%A9-2862
-   调研目的：评估是否能以可持续、合规、低维护的方式获取每日对局数据

## 1. 调研背景

每日战报生成器需要采集 1～4
个韩服主播账号当天的比赛记录，计算胜率、英雄胜率、KDA
等指标，并生成图片和文案。为了避免依赖 HTML 页面结构，当前优先调查 OP.GG
页面是否通过 Fetch/XHR 请求获取 JSON
数据，以及这些请求是否能支持项目需要的字段和分页。

社区代码库中存在针对 OP.GG 内部接口的第三方封装，提到接口前缀：

``` text
https://lol-web-api.op.gg/api/v1.0/internal/bypass/
```

这仅作为定位线索。它不代表该接口是官方公开
API、长期稳定接口或获准供第三方自动化调用的接口。实际请求
URL、参数、认证要求和返回结构必须通过真实页面请求验证。

## 2. 调研目标

### 2.1 必须回答的问题

1.  玩家页面如何解析或定位目标账号？
2.  页面请求中是否存在对局列表接口？
3.  是否存在单局详情接口，或对局列表本身已包含所需统计字段？
4.  请求是否返回 JSON？字段结构如何？
5.  是否支持分页、游标、数量限制或时间过滤？
6.  能否准确区分目标玩家在每场比赛中的数据？
7.  数据是否覆盖所需游戏模式？
8.  对局结束后多久会出现在页面/接口中？
9.  请求是否依赖 Cookie、动态令牌、内部编码键或其他会话信息？
10. OP.GG 的当前条款是否允许该自动化用途？
11. 相比 Riot 官方 API，OP.GG 路线的维护成本和风险是否可接受？

### 2.2 不在本次调研范围内

-   绕过验证码、登录保护、访问控制或速率限制。
-   伪造或窃取用户会话凭据。
-   对 OP.GG 服务进行高频压力测试。
-   大规模抓取大量账号或历史数据。
-   直接实现完整日报发布系统。

## 3. 合规前置条件

截至本计划书日期，检索到两类需要同时考虑的公开说明：

-   OP.GG 帮助中心在 2025-12-31
    更新的说明称，一般不禁止数据抓取或网页爬取，但指出商业使用、未标注来源或过量请求可能导致访问受限。
-   OP.GG 当前使用条款页面标注的最近更新日期为 2026-09-14，条款限制
    scraping/data
    mining，并限制使用自动化脚本收集信息或与网站服务交互；条款也对商业使用和内容再利用作出限制。

两者存在口径差异。不能只选取较宽松的一条作为生产部署依据。建议向 OP.GG
书面说明：个人/团队内部战报生成、每天 1～4
个公开账号、低频请求、公开发布到斗鱼鱼吧、标注来源、不会转售数据，并询问是否允许调用相关页面接口及需遵守的限制。

在获得明确答复之前： - 可进行低影响的页面观察和请求结构研究。 -
不应把内部接口投入无人值守的生产采集。 - 不应尝试规避
`401`、`403`、验证码、限流或访问控制。 - 不应把 Cookie、Authorization
或内部会话凭据复制进 GitHub Actions。 - 若许可不明确，优先评估 Riot 官方
API。

## 4. 调研方法

### 阶段 A：页面请求观察

**目的：** 确定页面实际加载数据的方式。

操作步骤：

1.  在浏览器中打开样例账号页面。
2.  按 `F12` 打开开发者工具。
3.  进入 `Network`，选择 `Fetch/XHR`。
4.  清空请求列表并刷新页面。
5.  观察与玩家资料、段位、近期对局、英雄统计相关的请求。
6.  点击"查看更多"、展开对局详情或翻页，观察新增请求。
7.  对可疑请求记录 URL、HTTP
    方法、查询参数、状态码、Content-Type、响应大小和响应 JSON
    的顶层结构。
8.  不记录或分享 Cookie、Authorization、令牌及个人会话信息。

**交付物：** 请求清单 `request-inventory.md`。

建议表格：

  ----------------------------------------------------------------------------------------------
  编号     触发动作       请求路径（脱敏）   方法       状态码   响应类型    用途猜测   待确认
  -------- -------------- ------------------ ---------- -------- ----------- ---------- --------
  R-01     打开玩家页     待填               GET/POST   待填     JSON/HTML   账号资料   是

  R-02     对局列表加载   待填               GET/POST   待填     JSON        对局列表   是

  R-03     展开单局       待填               GET/POST   待填     JSON        单局详情   是

  R-04     点击查看更多   待填               GET/POST   待填     JSON        分页加载   是
  ----------------------------------------------------------------------------------------------

### 阶段 B：接口字段分析

**目的：** 确认是否满足日报指标。

对响应字段逐项标注：

  --------------------------------------------------------------------------------
  目标字段          是否需要           预期来源             验证方式
  ----------------- ------------------ -------------------- ----------------------
  对局唯一 ID       必需               对局列表或详情       与页面对局逐条对应

  对局开始时间      必需               对局元数据           转换为 KST 后人工核对

  对局时长          推荐               对局元数据           与页面显示比对

  目标玩家身份      必需               玩家 ID / PUUID /    核对 Riot ID
                                       队伍参与者           和玩家数据

  英雄              必需               目标玩家统计         与页面显示比对

  胜负              必需               目标玩家或队伍结果   与页面显示比对

  击杀 / 死亡 /     必需               玩家统计             抽样核对
  助攻                                                      

  补刀              推荐               小兵和野怪统计       核实合计口径

  游戏模式          推荐               对局元数据           与页面标签比对

  分页标记          必需（如有分页）   游标 / offset / 页码 检查前后页重叠与缺失
  --------------------------------------------------------------------------------

应区分"字段未返回""字段为 null"和"字段值为 0"，三者语义不同。

### 阶段 C：账号定位分析

**目的：** 找到 Riot ID 到 OP.GG 内部账号标识的映射方式。

检查： - URL slug 是否仅用于展示，还是接口参数直接使用。 - 页面
HTML/初始状态中是否包含内部账号 ID。 -
接口是否需要额外的动态路径键或其他参数。 - Riot ID
中的中文字符、特殊字符和 `#` 标签如何编码。 -
账号更名或标签变化后，映射是否仍可靠。

只记录必要的公开标识；不要将账号定位机制扩展为绕过访问控制的手段。

### 阶段 D：分页与时间窗口验证

**目的：** 确保当天对局不漏算、不重复。

1.  检查默认每页数量。
2.  观察"查看更多"是否使用 offset、页码、游标或其他参数。
3.  记录相邻页面的对局 ID，检查重复与断档。
4.  确认列表是否按时间倒序。
5.  判断接口是否提供时间筛选；若没有，评估需要翻取多少页才能覆盖当天窗口。
6.  对重复请求进行小规模、低频验证，不开展压力测试。
7.  以 `Asia/Seoul` 作为统计时区，确认时间戳的时区与单位。

### 阶段 E：更新延迟与完整性验证

**目的：** 判断早间日报能否覆盖前一自然日的全部对局。

建议对单个测试账号在合法、低频的前提下进行人工观察： -
记录对局结束时间。 - 记录 OP.GG 页面首次显示该局的时间。 -
记录接口首次返回该局的时间。 - 比较对局 ID、英雄、胜负、KDA
等关键字段。 - 将观察结果记录为样本，不把单次观察当作普遍 SLA。

如无法保证数据在计划运行时间前更新，应增加人工补跑能力，并在战报中标明采集时间。

### 阶段 F：稳定性与错误行为验证

只在正常页面访问和允许范围内观察： - 常见成功状态码及响应结构。 -
是否出现 `429`、`401`、`403` 或服务端错误。 -
接口字段缺失、空列表、错误页返回 JSON 等情况。 -
页面或接口改版后是否可检测到结构变化。

遇到 `401`、`403`、验证码或明确访问限制时停止自动请求，不尝试绕过。

## 5. 候选接口线索

以下内容仅用于辅助定位真实页面请求，不作为已经确认可调用的接口规范：

-   第三方 GitHub 项目：`https://github.com/LimaTechnologies/op.gg-sdk`
-   该项目 README
    提到的内部接口前缀：`https://lol-web-api.op.gg/api/v1.0/internal/bypass/`
-   公开历史示例中出现过类似 `.../games/kr/summoners/{summoner_id}`
    的路径，但该示例较旧，不能直接作为当前生产实现。

必须通过当前页面的实际 Network 请求验证： - 完整 URL 和参数。 -
是否有动态键或短期参数。 - 请求方法和必要请求头。 -
返回字段和分页方式。 - 当前条款与授权状态。

不要将第三方 SDK 的示例键、旧接口 URL 或页面会话凭据直接硬编码到项目中。

## 6. 备选方案：Riot 官方 API

OP.GG 的帮助中心说明其对局历史基于 Riot Games 官方 API 数据；如果 OP.GG
内部接口不稳定或未获许可，Riot 官方 API 应作为重要备选。

备选调查需要确认： 1. Riot ID 到 PUUID 的解析流程。 2. 韩服平台路由与
Match-V5 区域路由的使用方式。 3. API Key 类型、有效期、申请条件和配额。
4. 公开发布战报所需的产品注册或政策要求。 5. 对局 ID
查询、详情字段、分页和时间过滤方式。 6.
目标账号的可用数据范围与数据延迟。

开发密钥可能有短有效期，不应在没有确认密钥类型和使用条件时直接部署为无人值守任务。需要以
Riot Developer Portal 的最新说明为准。

## 7. 采集原型设计

接口确认且许可条件满足后，先做单账号原型，不立即建设完整图片系统。

建议输出：

``` text
research-output/
├─ account-resolution.json
├─ match-list-sample.json
├─ match-detail-sample.json
├─ normalized-matches.json
├─ field-mapping.md
├─ validation-report.md
└─ logs/
```

原型功能： - 接收配置中的一个 Riot ID 和服务器。 - 获取账号标识。 -
请求有限数量的对局记录。 - 对每条记录做字段规范化。 - 输出 JSON 文件。 -
对关键字段缺失、请求失败、响应结构变化给出清晰错误。 -
不生成或上传未经验证的数据。 - 不保存认证凭据或不必要的个人信息。

## 8. 验收标准

### 技术验收

-   找到并记录账号定位、对局列表和必要详情的真实请求。
-   能解释每个关键字段的来源和含义。
-   能稳定地把对局列表映射到目标玩家。
-   对分页、去重、时间边界有可复现的验证结果。
-   至少抽样核对 10 场对局；如果当天不足 10
    场，可从近期记录中补充，但必须注明时间范围。
-   对失败状态和结构变化有检测逻辑。
-   生成一份字段映射与验证报告。

### 数据验收

-   对局 ID 不重复。
-   胜负、英雄、KDA 和对局时间与页面样本一致。
-   KST 日期过滤正确。
-   明确列出接口未覆盖的模式、缺失字段和潜在延迟。
-   不将采集失败误判为"当天无对局"。

### 合规验收

-   记录 OP.GG 当前条款与帮助中心的相关内容。
-   对自动化使用取得明确答复，或选择其他获准的数据来源。
-   不绕过访问控制，不把会话凭据写入代码仓库。
-   在公开输出中注明数据来源。

## 9. 风险登记表

  --------------------------------------------------------------------------------------------
  风险                    概率 / 影响             处置
  ----------------------- ----------------------- --------------------------------------------
  内部接口随时变化        中 / 高                 隔离适配器、响应校验、告警

  使用许可不明确          中 / 高                 书面询问；必要时改用 Riot API

  动态参数或会话要求      中 / 高                 不复制敏感凭据到无人值守任务；评估官方接口

  分页逻辑误判            中 / 高                 使用对局 ID 检查覆盖与重复

  更新延迟                中 / 中                 延后采集、补跑、标记采集时间

  某些模式无数据          中 / 中                 文档化覆盖范围，避免虚报完整

  账号标识变化            低至中 / 中             定期核验 Riot ID 与内部映射

  公开发布的政策要求      中 / 高                 确认 OP.GG 与 Riot 对公开展示的规则
  --------------------------------------------------------------------------------------------

## 11. 最终决策标准

满足以下条件时，才建议将 OP.GG 接口纳入生产方案：

-   使用条件得到明确确认。
-   目标账号和对局数据能稳定定位。
-   关键字段齐全且与页面数据一致。
-   分页和时间窗口不会造成明显漏数。
-   更新延迟适合每日战报。
-   无需绕过访问控制或依赖不应长期保存的会话凭据。
-   错误状态能被检测并安全退出。

若任一关键条件不满足，则改用 Riot 官方 API
或经确认获准的其他数据来源。即使原型可运行，也不代表接口获得官方支持或未来不会变化。
